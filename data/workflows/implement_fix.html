⚠ Why pie_batch_edit Failed (Session Lesson)

Root cause: old_string had a typo — [:20 instead of [:20] (missing closing bracket). Since pie_batch_edit requires exact string matching, the first 2 of 3 edits silently failed. Only edit 3 (a simple return-type annotation change) succeeded.

The deeper pattern: pie_batch_edit is brittle for complex multi-line blocks. It's ideal for isolated replacements (e.g. renaming a variable, adding a parameter). For function-body rewrites, individual edit calls are safer because each can be independently verified.

Debugging tip: When a batch edit fails, look at the summary field — it shows which edits applied and which failed. The first failed edit's old_string had an exact-match error. Read the actual file content around the target lines to spot differences in whitespace, line endings, or punctuation.

⏱ Patterns to Avoid (Token & Time Waste)

  • AVOID One edit per change when the same pattern repeats in one file. Use replace_all for renames, pie_batch_edit only for simple isolated replacements (variable renames, import additions). For multi-line function-body changes, individual edit calls are more reliable — batch failures cost more tokens to recover from.
  • AVOID Sequential Read of every file before starting edits. Batch with pie_batch_read or pie_file_api (pass paths=[...]). This session read ~15 files — could have been 4 batch calls instead of 15.
  • AVOID Double LLM call for streaming final answer — blocking generate followed by streaming generate_stream for the same turn. Restructure to use streaming from the start so the blocking call is never needed.
  • AVOID Re-reading freshly edited files to verify edits. Use Read with offset/limit targeting only the changed lines instead of the full file.
  • AVOID Providing full context_dump to the LLM when a targeted minimal_context_dump with the 5-8 relevant symbols suffices. The 3000-line dump in this project consumes ~25k tokens per read.
  • AVOID Multiple validation runs after every single fix. Apply 3-5 related fixes together, then run validation once. This session did 3 separate validation runs — could have been 1.
  • AVOID Reindexing atlas after non-kernel edits. Only kernel files need atlas regeneration. agent_core edits don't — save the 30s.
  • AVOID Back-and-forth on whether to implement a fix after a review request. If a reviewer flags an item as incomplete, fix it immediately rather than debating priority — the reviewer already decided it matters. This session spent 3 extra rounds on ToolResult after the first pass.
  • AVOID Inline TODOs that duplicate what's in the fix checklist. The session's todowrite items duplicated the diagnosis doc's checklist. Pick ONE source of truth — either the checklist or the todo list, not both. Keeping both in sync costs update tokens.

✅ Patterns to Follow

  • DO Read the fix plan first before touching any code. The diagnosis doc has specific fix code — follow it over your own inference. When the doc says "fix X by doing Y with code Z", use that code directly.
  • DO Group fixes by file — read a file, apply ALL its fixes, move on. Minimizes re-reading the same file.
  • DO Trace the full data flow before changing any value that passes through 3+ functions (e.g. tool_call_id chain: provider → parse → messages → convert). One missing link breaks the chain.
  • DO Add defense-in-depth — uuid fallbacks, null checks at EVERY consumer, not just the origin. A fix at the provider level is fragile; a fix at every consumer is robust.
  • DO Bump the checklist in the diagnosis doc after each fix batch — keeps the session state visible to future agents.
  • DO Run validation between fix batches (not after every single edit). Catches breakage early without the overhead of 10+ sequential runs.
  • DO When a reviewer asks for changes, verify the claim first by reading the relevant code, then apply the fix in one shot. Don't explain why you think it's unnecessary — just read, confirm, fix.
  • DO Batch file reads with pie_batch_read or pie_file_api with paths=[...] when you need context from 2+ files. This session's provider investigation read 3 files serially — one batch call would have saved 2 round trips.
  • DO Check blast radius with pie_find_impact before editing any symbol. Every symbol you modify may have dependents you don't see. Run pie_find_impact(name="symbol") during planning to surface all transitive dependents. Fix them in the same edit batch rather than discovering breakage at validation time.

🛠 New Tools That Would Accelerate This

  • TOOL pie_validate_imports(package) — Static circular import detection: resolves all import chains in a package and flags cycles. Would have caught the debate_ops circular import in tools/__init__.py without runtime trial-and-error.
  • TOOL pie_fix_checklist_sync(path) — Scans a markdown checklist, resolves each file:function() citation against the atlas, and auto-ticks items whose code matches the expected fix pattern. Keeps the checklist in sync with actual code state.
  • TOOL pie_mass_rename(old_name, new_name, file_pattern) — Rename a symbol across all files matching a glob, with rename refactoring awareness (function defs + all call sites). E.g. _STRING_ARG_KEYS → _SINGLE_ARG_TOOLS in 3 files. This session manually applied renames with 6 individual edits.

♻ Generalized Workflow (Any Issue)

The same 8-phase workflow applies to any issue-resolution task:

  1. SCOPE — Read task + devpt reports + diagnosis/fix plan. Identify BLOCKER vs HIGH vs MED/LOW. Understand the data flow for each fix. Read the AGENTS.md for workflow rules.
  2. TRACE — For each fix, read ALL files in the data flow chain (not just the symptom location). Map where values originate, transform, and terminate. Use pie_batch_read for 2+ files.
  3. PLAN — Group all edits by file. Check blast radius with pie_find_impact for every symbol you plan to edit. Identify repeated patterns (same change in 3 places) for batch. Identify cross-file patterns (same uuid fallback in 4 files) for parallel editing.
  4. FIX — Apply edits root-cause-first, defense-in-depth at every consumer. Read a file once, apply ALL its edits, move on. Use individual edit for multi-line blocks; use replace_all for isolated renames.
  5. VALIDATE — Run seed_hypotheses + validate_capabilities (or equivalent module tests). Fix regressions before moving on. Batch 3-5 fixes per validation run.
  6. DOCUMENT — Update status.md: add Recent Changes line, remove fixed Known Gaps, bump _Last verified. Append checklist ticks to fix plan. Update implement_fix.html with new patterns.
  7. OPTIMIZE — Review for: double work (blocking+streaming LLM calls), unnecessary re-reads, missed batch opportunities, argumentation loops with reviewer. Collapse into one source of truth.
  8. GENERALIZE — Create/update workflow HTML so future agents reuse the pattern instead of rediscovering it. Add any new tool suggestions discovered during the session.

🤖 Next-Agent Token & Time Optimization

Specific bottlenecks from this 18-issue session, quantified:

  • 27% Argumentation with reviewer — 3 extra rounds defending "ToolResult vs tc() wrapper" instead of reading the code and applying the fix. Fix: when a reviewer says something is incomplete, read the relevant code first, verify the claim, then fix — don't argue.
  • 20% Re-reading files for verification — full-file reads after every edit to confirm it applied correctly. Fix: use offset/limit reads targeting only changed regions, or rely on the edit tool's success signal.
  • 15% Maintaining two todo lists — todowrite items + diagnosis doc checklist in sync. Fix: Pick ONE source of truth (the diagnosis doc checklist). Delete the todowrite after syncing.
  • 12% Recovering from pie_batch_edit failure — failed batch + fallback to 25 individual edits + extra verification. Fix: verify old_string with pie_verify_edit before batch; prefer individual edit for multi-line blocks.
  • 10% Sequential file reads — 15 individual Read calls that could have been 4 batch calls. Fix: plan reads before starting. Read all files needed for the current fix group at once.
  • 8% Extra validation runs — 3 runs when 1 would suffice. Fix: apply all related fixes, THEN validate once.
  • 8% Context window waste — holding full-file content in session after editing unrelated functions in that file. Fix: after applying edits to a file, drop its full content from working memory and retain only the changed signatures.
